# M6.15 — Fixed GS cover-art cache

M6.15 adds the native storage layer for future game cover art. It is deliberately separate from game discovery: no image is displayed until a later catalog/provider supplies decoded RGBA pixels and a stable title key.

## Allocation strategy

PS2SDK's `graph_vram_allocate()` is a bump allocator. Its `graph_vram_free(address)` resets the pointer to the supplied address, so it is not a general-purpose free-list and cannot safely free arbitrary texture slots out of order.

NEXUS therefore reserves one contiguous PSMCT32 block after the framebuffers and built-in NXA1 atlas:

- Four fixed slots.
- Each slot: 128×128 RGBA32 = 65,536 bytes / 16,384 32-bit GS words.
- Total reservation: 512×128 PSMCT32 = 262,144 bytes (256 KiB).
- Each slot receives a deterministic GS base address inside that single reservation.
- LRU only selects which existing slot is overwritten. It never frees or reallocates a texture.

## Runtime API

`nexus_cover_cache_init()` reserves the block once. It is optional and non-fatal; if allocation fails, the shell remains usable.

`nexus_cover_cache_store(key, pixels, bytes)` accepts a 128×128 RGBA32 buffer of exactly 65,536 bytes, aligned to 16 bytes for GIF DMA. The cache marks the destination unavailable before transfer and only publishes the key after a successful DMA completion.

`nexus_cover_cache_find()` updates recency on a hit. `nexus_cover_cache_draw()` binds the selected slot with linear filtering and draws it at a caller-specified GS coordinate and size.

The key is a caller-supplied 32-bit stable identifier. The future library scanner must define a stable mapping (for example, a hash of source + title ID) and must handle collisions before using the cache.

## VRAM budget

The GS exposes 4 MiB of local memory. With the current renderer and the four artwork slots:

| Allocation | PAL | NTSC |
|---|---:|---:|
| Two 640-wide RGBA32 framebuffers | 2.50 MiB | 2.1875 MiB |
| Six-icon NXA1 atlas | 128 KiB | 128 KiB |
| Four cover slots | 256 KiB | 256 KiB |
| Total before alignment/other allocations | 2.875 MiB | 2.5625 MiB |
| Theoretical remainder | 1.125 MiB | 1.4375 MiB |

The calculations use the actual renderer dimensions and PSMCT32 bytes per pixel. Page/block alignment and future GS allocations must still be measured on runtime hardware before increasing the cache.

## Safety and current boundary

- No filesystem is mounted and no image is read from HDD/MMCE/USB yet.
- This milestone does not add a PNG/JPEG decoder, game scanner, cover metadata provider or visible coverflow.
- There is no arbitrary free operation and no runtime resizing of slots.
- If DMA packet allocation fails, an existing cache entry remains valid. If a transfer begins but fails, that slot is invalidated so stale artwork cannot be shown as the new title.
- The cache is single-threaded and assumes all operations occur on the native shell's render/main thread.

## Verification

Host tests exercise free-slot preference, least-recently-used selection, deterministic ties and invalid arguments. PS2DEV cross-build and full host CI must pass before treating this module as build-integrated. A PCSX2 / physical-PS2 run is still required to validate texture output and memory behavior.
