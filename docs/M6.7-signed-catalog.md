# M6.7 — Signed catalog trust

**Purpose:** make publisher authenticity a separate gate from package byte integrity.

## Signed envelope v1

The host Bridge client accepts only a raw JSON envelope with exactly these fields:

- schema: nexus.signed-catalog.v1
- key_id: identifier of a locally pinned signing key
- algorithm: Ed25519
- payload: unpadded base64url of the exact catalog payload bytes
- signature: unpadded base64url of the 64-byte Ed25519 signature

The signature is computed over the decoded payload bytes exactly as published. The verifier does not parse and re-serialize JSON before checking the signature.

The signed payload must be strict UTF-8 JSON with a packages array, integer issued_at and expires_at Unix timestamps, and a validity interval no longer than seven days by default. The verifier rejects duplicate JSON fields, non-standard constants, expired catalogs, future issue times outside the configured clock skew, unknown keys, malformed signatures, oversized payloads and unsupported algorithms.

## Key management

The trust policy receives a local keyring mapping key IDs to raw 32-byte Ed25519 public keys. There is no trust-on-first-use, remote key discovery or automatic key rotation. A release process must distribute and pin public keys through a separately trusted channel. Rotation and revocation remain explicit operator-maintained changes.

The host verifier uses the cryptography package; the dependency is declared in requirements-host.txt and installed by GitHub Actions. This is not a PS2-side Ed25519 implementation.

## Bridge integration

- BridgeClient.catalog() requires an explicit pinned trust policy and rejects unsigned JSON.
- Catalog records are normalized only after signature and schema verification.
- A package download is accepted only when the metadata exactly matches a record from the most recently verified signed catalog.
- The existing ranged download and SHA-256 checks remain in place. The signature authenticates the catalog statement; the package digest then binds downloaded bytes to that trusted statement.
- A later catalog verification failure clears the in-memory trusted package set.

## Safety boundary

This protects the host Companion/Bridge flow from unsigned or modified catalog metadata when the local public key is trusted. It does not prove that a package is safe, that the publisher's build process is uncompromised, or that a PS2-side client can verify Ed25519. It does not enable any device write or installer action.

Before production use, SPDW Factory must provision its own release signing key securely, keep private signing material offline or in a managed signing service, publish only the public key in a trusted release, and define a key-rotation/revocation procedure. The test signing key in unit tests is synthetic and must never be reused for releases.
