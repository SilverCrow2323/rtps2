# M6.13 — Embedded NXA1 atlas and boot initialization

M6.13 closes the path from original section artwork to the running shell without depending on a mounted filesystem.

## Boot path

1. The six 64×64 PNG sources live in `assets/icons/`.
2. The native EE workflow runs `tools/nexus_asset_pack.py` and creates `assets/build/NEXUS-ICONS.NXA`.
3. `src/nexus_asset_blob.S` aligns the NXA1 blob to 16 bytes and embeds it into the ELF read-only data section.
4. `nexus_renderer_init()` passes the embedded start/end symbols to `nexus_atlas_upload()`.
5. The EE-side validator checks the NXA1 header, exact dimensions and payload length, reserved bytes and SHA-256 payload digest before any texture VRAM allocation.
6. The atlas is uploaded by GIF DMA and becomes available to the dashboard cards.

No mass:/, HDD, MC, MMCE or USB mount is assumed. A failed asset upload is non-fatal: NEXUS keeps the procedural 5×5 glyph fallback and the renderer can continue.

## Memory / future artwork

The embedded atlas occupies 128 KiB of GS local memory. The double 640×512 32-bit framebuffer pair consumes approximately 2.5 MiB before alignment and metadata. The next graphics milestone must budget remaining GS memory explicitly before introducing cover-art textures; cover images will be streamed through bounded slots rather than pinned as one large atlas.
